# LLM에게 설치·Model Bay 관리를 맡기는 방법

**0.3.3 · DGX Spark / Ubuntu ARM64** · [English](LLM-GUIDE.en.md)

이 문서를 작업할 LLM에게 링크로 전달하세요. Spark 터미널/SSH 접근 권한이 있는 코딩 에이전트라면 설치와 등록을 실행할 수 있습니다. 일반 채팅만 가능한 LLM은 안내만 할 수 있습니다. 대시보드 자체에 LLM이 내장되거나 상주하지 않습니다.

## 먼저 구분하기

| 하고 싶은 일 | 사용 방법 | 바뀌지 않는 것 |
|---|---|---|
| 대시보드 설치/업데이트 | 공식 `.deb` + 초기 설정 | 모델·CUDA·드라이버를 설치/교체하지 않음 |
| 이미 설치한 ComfyUI/추론 서버 추가 | Model Bay → 서비스 추가 → 기존 사용자 서비스 선택 | 엔진 다운로드나 자동 시작 없음 |
| 서비스명·모델명·양자화·엔진명 수정 | 카드 연필 → 표시 정보 → 저장 | 표시만 변경. 실행 모델/명령은 그대로 |
| API 포트·앱 링크·제어 권한 변경 | 연필 → 연결 설정 → 검사 → 저장 | 엔진의 실행 인자/포트 자체는 변경하지 않음 |
| 카드 순서 변경 | 순서 → 이동 → 저장 | 실행 상태 변경 없음 |
| 다른 실제 모델로 교체 | 검증된 실행 프로필 추가 → 정지 → 상세에서 프로필 선택 → 시작 | 자동 교체/자동 복구/파일 삭제 없음 |
| 모델 파일 조회/목록 추가 | 모델 파일 → 지정 폴더 검색 → 목록 등록 | 가중치만으로 실행 서비스가 만들어지지 않음 |
| 새 엔진/가중치 설치 | Spark에서 별도 설치 후 사용자 서비스로 구성 | 대시보드에 자동 설치 마법사는 아직 없음 |

등록 단위는 **서비스 카드**, 실행 방법은 **프로필**, 가중치 후보 목록은 **모델 파일**입니다. 여러 파일을 등록하는 것과 여러 서버를 실행하는 것은 별개입니다. ComfyUI 체크포인트를 추가할 때마다 카드를 만들 필요는 없습니다. Hermes 공급자 변경은 Hermes 게이트웨이 서비스 등록과 별도입니다.

## 1. 대시보드 설치 요청문

아래 내용을 복사하고 필요한 조건을 바꾸세요. 비밀번호·API 키·개인 주소를 공개 채팅이나 GitHub 이슈에 넣지 마세요.

```text
이 Spark에 DGX-SPARK-Control을 설치해줘.
저장소: https://github.com/hvlfhvlf/DGX-SPARK-Control
먼저 docs/LLM-GUIDE.ko.md, AGENTS.md, docs/QUICKSTART.ko.md,
docs/UPDATES.md와 선택한 릴리스 기록을 읽어.
OS/아키텍처와 기존 패키지·압축판 설치 여부를 확인하고,
공식 릴리스의 ARM64 .deb와 SHA256SUMS를 받아 검증 후 설치해.
기존 설정·비밀번호·로그인·모델·드라이버·Tailscale 설정은 보존해.
초기 비밀번호는 내가 Spark의 설정 화면이나 대화형 터미널에서 직접 입력할게.
접속 주소, 인증 상태, 서비스 자동 시작 설정, 메모리 상한을 검증하고
실제로 수행한 단계와 아직 확인하지 못한 단계를 구분해서 알려줘.
실행 중인 모델은 중단하지 말고, 외부 공개/Funnel은 설정하지 마.
```

LLM의 실행 순서:

1. `uname -m`, OS 정보와 `dpkg-query -W dgx-spark-control` 등으로 설치 유형을 확인합니다. 미설치는 정상적인 분기입니다. 패키지판/압축판 업데이트를 혼용하지 않습니다.
2. [공식 릴리스](https://github.com/hvlfhvlf/DGX-SPARK-Control/releases/tag/v0.3.3)의 `.deb`와 `SHA256SUMS`를 같은 비공개 작업 폴더에 받습니다. 선택 버전과 파일명, 체크섬 대상이 일치해야 합니다.
3. 다음 명령을 다운로드 폴더에서 실행합니다. 검증 결과에 해당 `.deb`가 **OK**로 표시된 것을 확인한 뒤 설치합니다.

```bash
sha256sum --ignore-missing --check SHA256SUMS
sudo apt install ./dgx-spark-control_0.3.3_arm64.deb
dgx-spark-control setup --check
dgx-spark-control setup --cli --lang ko
```

4. `setup`은 일반 Spark 사용자로 실행합니다. GUI는 `dgx-spark-control setup`입니다. 새 비밀번호는 사용자가 대화형으로 입력합니다. 기존 비밀번호가 있을 때만 `setup --non-interactive`가 가능합니다. 비밀번호를 명령 인자·스크립트·환경 변수·응답에 넣지 않습니다.
5. 패키지 설치 성공과 런타임 정상은 따로 확인합니다. `setup --check`, `systemctl --user is-active dgx-spark-control.service`, `is-enabled` 결과와 실제 인증된 브라우저를 확인합니다. 부팅 후 동작은 사용자 서비스와 linger 설정을 검사해 설명하고, 실제 재부팅 검증과 구분합니다.
6. Spark 로컬 주소는 `http://127.0.0.1:8767`입니다. 휴대폰에는 감지한 Tailscale HTTPS 주소를 안내합니다. 앱별 주소와 대시보드 주소를 혼동하지 않습니다. Serve/접근 정책 변경은 별도 요구가 있을 때만 기존 설정을 확인하고 처리합니다.
7. 서버+트레이 cgroup의 `MemoryMax=503316480`, `MemorySwapMax=0`을 유지합니다. `MemoryCurrent` 관측치를 적되 실제 추론 성능 비교라고 부르지 않습니다.

업데이트는 새 `.deb` 설치 후 같은 검증을 합니다. 대시보드/트레이는 다시 시작될 수 있지만 모델을 재시작하는 단계가 아닙니다. 초기 설정 화면에서 기존 비밀번호를 보존하려면 비밀번호 칸을 비워 둡니다. [복구 안내](UPDATES.md)를 먼저 읽고 알려진 정상 패키지로 되돌릴 경로를 확보하세요.

## 2. 설치된 서비스를 Model Bay에 추가

```text
이 Spark에 이미 설치된 <서비스/엔진 이름>을 Model Bay에 추가해줘.
docs/LLM-GUIDE.ko.md와 docs/MODELS.md를 읽고 기존 등록부터 확인해.
작동하는 서비스·가중치·드라이버를 재설치하지 말고 다른 카드도 보존해.
사용자 systemd unit, 실제 로컬 API 포트, 사용자가 접속할 앱 주소를
각각 확인하고 지원되는 어댑터를 선택해. 조회되지 않는 값은 추측하지 마.
웹의 서비스 추가 또는 revision 검사 있는 services CLI로 등록해.
제어 권한은 내가 요청한 서비스에만 허용해. 등록만 하고 자동 시작하지 마.
무엇이 등록되었고 무엇은 별도로 설치/설정해야 하는지 알려줘.
```

우선 웹의 **서비스 추가 → 기존 실행 서비스 선택 → 연결 유형/로컬 API 포트/앱 주소 → 제어 여부 → 연결 검사 → 저장**을 사용합니다. 검색은 사용자 systemd 서비스 후보이며 모든 포트나 디스크를 스캔하지 않습니다. 정지 서비스는 준비 상태를 확인하지 못한 채 등록할 수 있습니다. 등록 후 시작은 별도 동작입니다.

지원 manager는 `systemd-user`입니다. 터미널 프로세스·Docker·시스템 서비스를 직접 관리하는 기능은 없습니다. 새 user unit이 필요하면 기존 실행 방법, 작업 디렉터리, 환경 파일, 종료 동작을 확인해 로컬에 작성합니다. 실행 중인 프로세스를 중복 실행하거나 기존 unit을 임의 교체하지 마세요. 모델을 대시보드의 cgroup에 넣지 않습니다.

API 관측용 `probe.origin`은 Spark의 `http://127.0.0.1:PORT`이며, 브라우저용 `open_url`은 접속 기기에서 열 수 있는 앱 주소입니다. 둘은 같을 필요가 없습니다. 인증이 필요한 엔진 API에 키를 URL로 넣지 마세요. 현재 secret reference 연동은 없으므로 지원되지 않으면 프로세스 상태만 표시합니다. `/v1/models` 성공은 실제 추론 성공을 보증하지 않습니다.

## 3. 표시 수정과 실제 모델 교체 요청문

표시만 바꿀 때:

```text
Model Bay의 <카드>에서 표시 정보만 바꿔줘.
서비스명=<값>, 모델 풀네임=<값>, 양자화=<검증된 값>,
추론 엔진=<값>, 서빙 엔진=<값>. 모르는 값은 비워 둬.
카드 연필의 표시 정보에서 저장하고, <원하는 순서>로 정렬해.
실행 프로필·unit·포트·모델 파일·서비스 실행 상태는 변경하지 마.
저장 후 새로고침과 다른 화면 재진입으로 반영 여부를 확인해.
```

실제 모델을 추가/교체할 때:

```text
<서비스 카드>에 <새 모델/엔진> 실행 프로필을 추가해줘.
현재 프로필과 파일은 보존하고 새 프로필에 별도 ID를 사용해.
기존 설치 여부, 정확한 가중치/양자화, ARM64/GB10 호환성,
필요 메모리·디스크·포트와 다른 실행 작업을 먼저 확인해.
새 다운로드가 필요하면 출처/리비전/크기/라이선스와 실행 변경점을 설명해.
기존 registry에 병합하고 check 및 revision 검증 후 적용해.
이번에는 등록까지만 진행하고 실제 정지·전환·시작은 하지 마.
이전 프로필로 복구하는 방법과 미검증 항목을 함께 알려줘.
```

전환까지 원하면 마지막 두 문장을 “지정한 서비스의 정지 → 프로필 선택 → 시작까지 진행하되 다른 작업은 중단하지 마. 준비 상태와 작은 추론 검증도 확인해.”로 바꿀 수 있습니다. 실행 권한 범위를 사용자 요청에서 판단하며 이미 허용된 단계를 반복 확인할 필요는 없습니다. API 준비, 실제 생성 성공, 성능 검증은 별도 결과로 보고합니다.

## 4. LLM/운영자용 로컬 등록 절차

고급 의존성·타임아웃·프로필 작업은 [서비스 문서](MODELS.md), [상세 인계 절차](development/SERVICE-HANDOFF.ko.md), [일반 예제](development/SERVICE-REGISTRY.example.json)를 따릅니다. 예제 전체를 기존 registry 위에 덮어쓰지 않습니다.

```bash
umask 077
dgx-spark-control services export > ~/.local/share/dgx-spark-control/services-edit.json
# 이 비공개 파일을 로컬에서 백업하고 필요한 항목만 병합한다.
dgx-spark-control services check --file ~/.local/share/dgx-spark-control/services-edit.json
dgx-spark-control services apply --file ~/.local/share/dgx-spark-control/services-edit.json --expected-revision N
```

- `N`은 export 파일의 실제 revision입니다. 유효성 검사에서 `missing_units`도 확인합니다. `export`는 registry가 없으면 초기화하므로 설치 전 순수 조회 명령이 아닙니다.
- revision 충돌은 강제 덮어쓰지 말고 새로 export하여 변경을 다시 병합합니다. apply는 원자적 저장이며 서비스를 시작하지 않습니다.
- 실행 중 프로필을 다른 unit에 재연결하지 않습니다. 실패 시 실제 상태·최근 실패 원인·포트·가용 메모리를 먼저 확인합니다. 반복 재시작, 임의 프로세스 종료, 시작 제한만 무작정 초기화하는 루프를 만들지 않습니다.
- 비공개 registry·키·개인 주소·실행 인자·원본 로그는 채팅/저장소/이슈에 출력하지 않습니다. 검증 보고에는 성공 여부와 정제한 오류 요약만 씁니다.

## 0.3.3: 자동 시작·Harness·앱 유지관리

- 업데이트를 연결하기 전 [서비스 업데이트 안내](SERVICE-UPDATES.md)를 읽고 실제 서비스 유닛·설치 위치·데이터·런타임·공식 소스와 채널을 확인합니다. 개인 연결 파일은 로컬에서 백업하며 공개하지 않습니다. 웹에서 임의 설치 명령을 실행할 수 없습니다.
- 모델 등록·교체만 요청받았다면 부팅 자동 시작을 임의로 켜지 않습니다. 의존성과 동시 실행 메모리를 검토하고, 실행 대상을 바꾸기 전 이전 프로필의 자동 시작을 끕니다. 검증만을 위해 재부팅하지 않습니다.
- Harness에는 토큰 없는 HTTPS 앱 주소를 설정합니다. 앱 열기는 현재 시작 토큰에 맞는 인증 주소를 필요할 때 얻습니다. 토큰을 등록 필드·로그에 복사하지 않습니다. 프로세스 실행과 별도 추론 서버의 준비 상태를 구분합니다.
- 대시보드 패키지 업데이트 요청만으로 다른 앱을 정지·업데이트하지 않습니다. 대상 앱·버전을 확인하고 허용된 범위에서 정지한 뒤 검토형 업데이트를 진행합니다. 백업·검사·복구 결과를 나눠 보고하고 기본 CLI/import 검사만으로 전체 작업 호환성을 보장하지 않습니다.
- 기존 설정·기기 로그인·모델·관련 없는 프로세스를 보존합니다. 설치 버전·정확한 릴리스/커밋을 보고하고 개인 검증 자료는 저장소 밖에 둡니다.
