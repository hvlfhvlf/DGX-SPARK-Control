# 0.3.3~rc1 — local candidate

Adds an authenticated app-launch handoff for the existing local DeepSeek Harness installation. Model Bay registration remains private and device-specific. No GitHub publication is included.

The process adapter retains its meaning: running process is not verified model readiness. The fixed `deepseek-harness.service` integration reads at most 64 KiB from the local Harness startup log only after an authenticated POST, registry revision check, explicit control permission and running-state check. The HTTPS destination must match the configured app origin. A fixed loopback authentication exchange must succeed without redirects. A temporary URL is returned with no-store headers; neither registry/listing nor logs receive the token. Existing app authentication remains enabled.

No model lifecycle or inference request is required to register/open the app. A Harness restart rotates its startup token; the next open reads the latest log entry. The integration supports the existing local layout and port 3080, not arbitrary log files or remote engines. Errors fail closed with a generic message. Rollback uses the known-good 0.3.2 package and a private registry backup if required. This candidate does not change registry/auth schema.

Validation: 63 Linux Python and 40 JavaScript tests passed, including authenticated endpoint/origin rejection, stale revision, stopped service, changed token, mismatched destination, invalid redirect and browser handler dispatch. Chrome verified Model Bay → Open App → authenticated Harness UI → one short Qwen response. Existing workload PIDs/invocations and dashboard auth/config file hashes were preserved. Actual Harness stop/restart was not performed against the live workload; token rotation is covered by the isolated fixture. Physical iPhone testing is not claimed.
