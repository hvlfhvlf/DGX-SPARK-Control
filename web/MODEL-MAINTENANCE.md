# SPARK CONTROL — 모델 유지보수 가이드

현재 단계: 디자인 프로토타입. 이 문서의 서버 구성은 구현 계획이며, 설치·삭제·실제 검색 기능은 아직 연결되어 있지 않습니다.

## 다른 LLM에게 전달할 요청문

> 이 프로젝트의 MODEL-MAINTENANCE.md를 먼저 읽어라. 요청받은 모델 설치·교체·제거 범위 안에서 현재 파일 경로, 엔진, 서비스, 실행 중인 작업과 메모리 여유를 확인하라. 화면 코드를 모델별로 고치기보다 등록 정보와 엔진 어댑터를 갱신하라. 변경 전후 차이와 검증 결과를 남기고, 미확인 기능은 사용 불가로 표시하라. 검색만 요청받았다면 설치·삭제·실행하지 말라. 현재 프로토타입 단계에서는 실제 DGX 연동을 별도로 요청받기 전까지 목업만 수정하라.

## 권장 구조

- 모델 검색기: DGX 백엔드가 허용된 모델 폴더, Hugging Face 캐시와 설치된 엔진의 모델 목록을 읽는다. 브라우저는 DGX 파일시스템을 직접 검색하지 않는다.
- 등록 정보: 이름, 고유 ID, 실제 경로·리비전, 파일 형식, 엔진 종류, 검증된 제한과 기능을 보관한다.
- 실행 어댑터: 시작·정지·준비 상태·메트릭 수집을 엔진별로 구현한다. 임의 셸 문자열을 브라우저에서 받아 실행하지 않는다.
- 개인화: 사용자/기기별 화면 취향은 모델 등록 정보 및 시스템 운영 설정과 분리한다. 현재는 브라우저 localStorage에 저장한다.
- 화면: 등록 정보와 기능 지원 여부를 읽어 카드와 버튼을 그린다. 기존 어댑터가 지원하는 모델 교체에는 화면 수정이 필요 없도록 한다.

향후 서버 파일 예시: `config/models.json`, `schemas/model.schema.json`, `adapters/`, `discovery/`. **현재 이 서버 파일들은 존재하지 않는다.** 현재 목업 등록 배열은 `app.js`의 `models`, 개인화 및 검색 예시는 `preferences.js`에 있다.

## 등록 정보 계약 예시 (계획)

```json
{
  "schemaVersion": 1,
  "id": "local-example-q4",
  "displayName": "Local example",
  "source": {"kind": "local", "path": "/configured/models/example.gguf", "revision": null},
  "format": "gguf",
  "engine": {"adapter": "llama.cpp", "profileId": "reviewed-profile"},
  "capabilities": {"chat": null, "vision": null, "tools": null},
  "limits": {"contextTokens": null, "memoryEstimateGiB": null},
  "lifecycle": "needs_setup",
  "verifiedAt": null
}
```

`null`은 미확인이다. 파일명만으로 컨텍스트, 도구 호출, 메모리 사용량, DGX 호환성을 추정해 확정하지 않는다. 실행 중인 엔진의 `/models` 목록만으로 설치된 모든 파일을 찾았다고 주장하지 않는다.

## 검색과 등록

1. 설정된 경로만 탐색한다. 재귀 범위와 심볼릭 링크 경계를 제한하고 모델 가중치 전체를 주기적으로 읽거나 해시하지 않는다.
2. GGUF, 설정 파일, safetensors 인덱스·샤드, 다운로드 완료 여부 등을 확인한다. 샤드 여러 개를 서로 다른 모델로 등록하지 않는다. ComfyUI 체크포인트·LoRA도 실행 서비스와 구분한다.
3. 경로·리비전·엔진 고유 식별자로 중복을 정리하고 기존 등록 정보와 비교한다.
4. 신규 / 등록됨 / 누락 / 접근 실패 / 불완전 다운로드 / 지원하지 않는 엔진으로 분류한다. 접근 실패를 삭제로 해석하지 않는다.
5. 신규 결과를 검토한 뒤 초안으로 등록한다. 파일을 발견해도 자동 실행하거나 다운로드하지 않는다.
6. 누락 항목은 기록을 유지하고 실행을 막는다. 재검색 또는 명시적인 등록 해제 후 정리한다.

검색 시점은 수동 검색과 설치·제거 완료 직후를 우선한다. 주기적 검색은 저빈도 메타데이터 확인으로 설계한다. 현재 프로토타입의 검색 결과는 고정 예시이며 실제 경로는 읽지 않는다.

## 설치 / 교체 / 제거 절차

1. 요청 범위, 현재 등록 정보·설정 백업, 디스크·메모리 여유와 실행 중인 작업을 확인한다.
2. 설치는 출처·리비전·양자화·엔진 버전을 기록하고 다운로드 완료와 파일 구성을 검증한다. 기존 모델과 충돌하지 않는 경로에 둔다.
3. 기존 엔진 어댑터 사용이 가능하면 등록 정보만 추가한다. 새 엔진이면 어댑터 구현 및 상태/제어/메트릭 계약 검증이 필요하다.
4. 스키마 검증, 경로 확인, 실제 엔진 준비 상태 확인과 짧은 추론 테스트를 수행한다. 교체 시 포트·서비스·작업 충돌을 확인한다.
5. 모델 추가·교체·삭제 요청이 실제 실행을 포함하는 범위에서만 진행한다. 제거할 때 등록 해제, 프로세스 정지, 모델 파일 삭제를 서로 구분한다. 공유 캐시·샤드·다른 서비스의 참조를 확인한 후 요청된 파일만 처리한다.
6. 재검색으로 카드·상태·메모리 표시를 확인하고, 실패 시 이전 등록 정보와 실행 프로필로 복구한다. 설치 완료와 추론 검증 완료를 따로 보고한다.

완료 보고: 변경한 모델/경로/서비스, 등록 정보 차이, 테스트 입력과 성공 여부, 미검증 기능, 복구 방법. 키·토큰·사용자 프롬프트 내용은 로그에 남기지 않는다.

## 프로토타입 사용법

설정에서 `SCAN DEMO MODELS` → `REVIEW` → `ADD DRAFT`를 누르면 Models 화면에 `NEEDS SETUP` 카드가 추가된다. 실행은 비활성화되어 있다. 이 초안과 검색 결과는 새로고침하면 초기화된다. 개인화 설정은 같은 브라우저에 유지된다.
